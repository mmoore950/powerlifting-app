# Local portable annotation capture proposal

October 8, 2026. Proposal only; no product export control or packaging implementation.
Uses the actual `VideoAnalysisView`, `VideoModel`, `VideoImportStore` and
`BarFrameBundleExporter` source. Planner approval is required before implementation.

## Smallest useful flow

In Bar path, after explicitly importing a video and selecting a range, offer
**Export annotation window**. Initially require a positive range of at most one
second; explain this beside the control and let the existing start/end controls
adjust it. Do not silently shorten a selected rep or change ordinary 30-second
analysis. Keep automatic/manual choice; manual capture requires its existing seed.
Ask for squat/bench/deadlift if unset, and explain that the export includes the
imported movie, captured frames and analysis for local labeling. No labels or
tracking-accuracy verdict are generated by pressing Export.

Prepare a verified local package, then offer **Save to Files**. Successful capture
and successful destination save are separate states. Cancellation or failure
retains the previous analysis, shows an actionable error and permits retry. The
app sends no video to its backend or CI. Files destinations can be local or a
user-selected cloud provider; an explicitly on-device destination is needed for
an entirely local handoff. Choosing a destination is an actual user decision.

## Portable bytes and association

Use one fresh directory with the unchanged capture files at its root:

| File | Association |
| --- | --- |
| `<managed UUID>.mov` or `.mp4` | Exact imported source bytes at ledger `clip.localPath` |
| `frames/frame-NNNNNN.png` | Same accepted native images and ledger hashes |
| `ledger.json` | Original bytes, original integer CMTime components and session identity |
| `prediction.json` | Original bytes whose digest is in the ledger association |
| `bundle.json` | Original embedded ledger text/image bytes for the offline panel |
| `export-receipt.json` | Proposed supplementary file sizes/digests and package completion evidence |

Set context `assetRoot` to the managed movie's parent and `localPath` to its safe
basename before capture. Copy that basename into the package root. Do not rename
the movie after capture or rewrite ledger/bundle/prediction JSON to fit a new path.
The copied managed movie may differ from the user's original Photos asset; the
captured managed bytes, not a guessed original, are the verification source.
Resolve the final package as the CLI `--asset-root`; open its `bundle.json` for
labeling and use the strict native wrapper with its matching ledger/prediction.

Package only this completed capture's named regular files. Validate names, reject
symlinks/extra files, stream-copy the movie in bounded chunks, compare its digest
with the ledger and recheck source identity. Verify all PNG/prediction/bundle
digests and exact count/time/session association before publishing a fresh owned
directory. Write the supplementary receipt last. It records mechanical association,
not permission authenticity, native-origin attestation or representative accuracy.

## Ownership, storage and cancellation

The current model waits for capture before deleting its managed source, but the
completed capture directory contains no movie. A packaging operation must join
that same lifecycle: retain the source until the movie copy is verified, revoke
publication before replacement/removal, cancel copying cooperatively and await
cleanup before deleting the managed movie. A second task outside that join would
reintroduce a deletion race. Review actor/generation ownership before adding UI.
The existing capture authorization becomes inactive when capture publishes; a
portable operation needs its own generation-bound publication token and an outer
joined task covering capture plus packaging. Do not reuse the consumed token.

After package publication, give the Files picker a stable independent directory
lease. Removal of the managed movie cannot invalidate the saved package. Keep
the directory until picker completion/cancellation and any retry choice; never
delete while a provider is reading it. Scene transitions and picker presentation
must be checked against the view's existing cancel-on-disappear/inactive behavior.
Keep at most one prepared package; explicit discard and owned startup cleanup
must preserve completed user destinations. Never overwrite an existing package.

Proposed bounds: retain existing source <=500MiB, <=1s/16frames, PNG total32MiB,
bundle JSON48MiB, and add total physical package <=600MiB with every file counted.
The embedded PNGs and separate PNG files both occupy disk. A source export copies
the entire imported movie even for a one-second window; communicate its measured
size. Preflight free space for capture staging, package and possible provider copy
with conservative headroom (proposed1.4GiB at the maximum). Free-space checks are
advisory; handle write failures and cancellation without publishing partial output.
Do not load the full movie into `Data` or a single in-memory FileWrapper.

## Platform route and unresolved acceptance

Recommend a disk-backed directory/package and UIKit's
[`UIDocumentPickerViewController(forExporting:asCopy:)`](https://developer.apple.com/documentation/uikit/uidocumentpickerviewcontroller/init(forexporting:ascopy:))
in copy mode, bridged into the existing SwiftUI screen. Apple's documented API
exports URLs and has been available since iOS14. Directory/package handling,
provider copying and callback lifetime still need a native prototype; this is a
recommendation, not evidence that our package already saves successfully.
Apple also documents directory packages through
[`FileDocument.fileWrapper(configuration:)`](https://developer.apple.com/documentation/swiftui/filedocument/filewrapper(configuration:)).
That support alone does not establish bounded movie memory or our export behavior.
Do not add a ZIP dependency or rewrite the app around document storage silently if
directory export is unsuitable; return the concrete native result to the planner.

Caller metadata must remain honest: real footage `synthetic:false`, development
split initially, actual chosen lift and existing near-side-hub target. Use stable
recording identity across repeated windows/imports of the same source hash; never
give each window an independent research group. Subject/session independence is
unknown unless explicitly collected, and this initial flow cannot create holdout
evidence. Populate detector version/build from actual maintained algorithm and
app-build identifiers; no invented Git SHA or guessed provenance. Explicit local
export selection can be recorded as that action, not generalized research consent.

## Decisions, tests and size

Recommend planner approval of: one-second-only entry point; whole unchanged movie
in a600MiB disk-backed package; one prepared-package retention/retry; Files copy
prototype; development-only metadata with stable recording grouping. Full-rep
export remains separate: distinct window IDs, same original recording/group/split,
absolute accepted timestamps and conflict/seam checks before aggregation. A
one-second capture cannot establish complete rep performance.

Meaningful generated tests: successful package hashes/strict-wrapper handoff;
removal/replacement during source copy with no stale publication; cancellation
before/after publication and picker lease; mutated source/PNG/prediction rejection;
existing destination preservation, file/byte/storage failures and partial cleanup.
Native UI/device checks must exercise destination save, cancel/retry and leaving
the screen. Use generated media only for CI. Real private contribution also needs
authorized Apple access and the outstanding browser/privacy gate.

Provisional implementation size50–85minutes after approval, with lifecycle and
Files/provider uncertainty; no hard source deadline. First native result15–22minutes
after runner start provisionally, build8/test10/job30 limits, queue excluded.
Package/private-use readiness additionally needs actual local save and browser
handoff. Research readiness requires representative reviewed real annotations;
there is no reliable date until access and an initial labeling sample exist.
